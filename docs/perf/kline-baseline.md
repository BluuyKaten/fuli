## 二、前端数据处理（Node + 真实 @vue/reactivity）

模拟 `loadData` 的完整工作量：构造 candles → 12 遍指标计算（MA×4 / MACD×3 / BOLL×3 / KDJ×3 / RSI）。对比裸数组与 `reactive()` 深度代理数组。

| 数据集 | 根数 | 体积 | JSON.parse | 指标（裸） | 指标（reactive） | 倍数 |
|---|---|---|---|---|---|---|
| 000012.SZ | 5,071 | 1,016 KB | 3.5 ms | 11.2 ms | **91.4 ms** | **8.2×** |
| 600519.SH | 1,558 | 332.5 KB | 1.0 ms | 1.1 ms | **26.9 ms** | **24.5×** |

**这一行是 `ref` → `shallowRef` 的直接依据**：指标算法本身只要 11 ms，经过深度响应式代理后变成 91 ms。差的 80 ms 全部是 Proxy 创建与字段劫持，不是业务计算。

## 三、数据库层（EXPLAIN ANALYZE）

| 3 年窗口（600519.SH） | 727 | **0.97 ms** |

## 四、归因

以最坏场景（日线 5,071 根）拆解 214 ms 的总耗时：

| 环节 | 耗时 | 占比 |
|---|---|---|
| MySQL 查询 | 6 ms | **2.8%** |
| 序列化 + Feign + 传输 | 117 ms | **54.7%** |
| 前端指标计算（reactive） | 91 ms | **42.5%** |

**数据库从来不是瓶颈。** 这份基线最大的价值是否定了「几百万行导致卡顿」这个直觉假设。

## 五、实测推翻的三个假设

Phase 0 的意义就在这里：有三个此前的判断被实测否定了，方案必须相应修正。

### 1. 分钟线不是 5,000 根，是 240 根

`EastMoneyDataSource.java:56` 的 URL 里写着 `lmt=5000`，但实测 1 分钟线只返回 **240 根**——正好是一个交易日的分钟数（时间戳跨度 19,740 秒 ≈ 5.5 小时）。东方财富对 1 分钟线只提供当日数据，`lmt` 参数对它不起作用。

**影响**：原计划「分钟线限制根数 + 服务端聚合降级」是打空靶。22 KB 不需要限根，也不需要降级。分钟线真正的问题是 **249–1013 ms 的延迟波动**（3 倍抖动），来自外部 API，与数据量无关。

**修正**：分钟线的优化目标从「减少数据量」改为「减少外部调用次数」——缓存当日分钟线 10 秒，让用户在切股票、切周期、切回来时不再穿透外部 API。

### 2. 日线最大体积是 1 MB，不是 358 KB，也不是 3 MB

单股日线的体积差异很大：600519.SH 只有 1,558 根（332 KB），而 000012.SZ 有 5,071 根（1,016 KB）。

**影响**：日线确实存在「跨度大就卡」的场景，但触发条件是**老股票**（数据完整），不是所有股票。这解释了为什么卡顿是间歇性的、换个股票就好了。

### 3. Feign 开销不可忽略

同一份数据，经 trade-service 中转需 43.9 ms，直连 data-service 只需 37.0 ms——**Feign 序列化 + 转发固定开销约 7 ms/次**，且响应体还膨胀了 27 KB（332.5 → 360.2 KB，因为外层包了 `code/message/data`）。

**影响**：缓存应该放在 **data-service**（数据源头），而不是 trade-service。放在上层只是缓存了 Feign 的开销，下层依旧穿透。

---

## 六、基线结论

1. **DB 占 2.8%，优化 DB 的收益上限就是 2.8%**。ADR-0003 的字段瘦身仍然值得做（索引体积影响长期容量），但要清楚它不是解决卡顿的手段。
2. **传输占 54.7%**，视窗化（ADR-0002）是主要手段。
3. **前端占 42.5%**，`shallowRef`（Task 4.1）是投入产出比最高的一行改动。
4. **分钟线是另一条完全不同的链路**，瓶颈在外部依赖的延迟抖动，缓存优先于降级。

### Phase 2 + 4.1 复测结果（2026-11-03，已填）

| 指标 | Phase 0 基线 | 现在 | 变化 |
|---|---|---|---|
| 日线响应体积（默认） | 1,016 KB（5,071 根全量） | **146.7 KB**（620 根） | **-86%** |
| 日线响应耗时 | 122.7 ms | 未变（体积已降，耗时受 Feign 主导） | — |
| 分钟线冷请求 | 249–1013 ms | 253 ms | 持平（外部 API 决定，无法优化） |

**说明**：日线响应耗时没有明显下降，因为传输体积虽然降了 86%，但单次请求的固定开销（Feign 转发 7ms + 序列化 + 连接）占大头。真正的收益在**前端**——少解析 4,451 个对象、少跑 12 遍指标遍历。这个收益必须用浏览器 Performance 面板才能测出来，Node 基准只覆盖了计算部分。

### Phase 3 复测结果（2026-11-03，已填）

日线两级缓存上线后（L1 ConcurrentHashMap 10 min + L2 Redis 30 min）：

| 场景 | 冷请求（查库） | 缓存命中 | 倍数 |
|---|---|---|---|
| 600519.SH（620 根） | **190.9 ms** | **3.7 ms** | 约 45× |
| 000012.SZ（620 根） | 28.2 ms | **3.9 ms** | 约 7× |

Redis 中确认写入：`kline:daily:600519.SH`、`kline:daily:000012.SZ`。

**注意 190.9 ms 比 Phase 0 的 43.9 ms 慢**，但不是回退：Phase 0 测的是全量 1,558 根、且 buffer pool 和 JIT 都是热的；这次是服务刚启动、缓存全空、还要额外加载 800 根。命中后的 3.7 ms 才是稳态。

**剩余 3.7 ms 的构成**：HTTP + 620 次 `toMap`（每次新建 HashMap）+ 146 KB JSON 序列化。继续压只能改 DTO（用 record + 数组化字段），收益有限，暂不做。

### 浏览器端性能（2026-11-04，puppeteer + CDP `Performance.getMetrics`）

`ScriptDuration` 即 DevTools Performance 面板里的 "Scripting" 累计值。

| 指标 | `shallowRef`（现状） | `ref`（对照） |
|---|---|---|
| 首屏 ScriptDuration | 188.8 ms | 179.5 ms |
| 首屏 TaskDuration | 473.4 ms | 459.3 ms |
| 切股票 Script 增量 | 110.9 ms | 106.0 ms |
| 切股票 Task 增量 | 196.5 ms | 190.7 ms |

**`ref` 反而略快，差异在噪声内。`shallowRef` 的收益已被窗口化吃掉。**

Phase 0 测出 8.2 倍差异时数据是 5,071 根，Proxy 开销约 80 ms；窗口化后只有 620 根，Proxy 开销按比例降到约 10 ms，淹没在 190 ms 的 Script 总量里。

**这条结论对报告更有用**：两个优化在收益上重叠而非叠加。只做 `shallowRef` 不做窗口化，省 80 ms；先做窗口化，这 80 ms 自动变成 10 ms。所以不该把 `shallowRef` 当成性能卖点。

### 交互功能验证（2026-11-04）

| 功能 | 判据 | 结果 |
|---|---|---|
| 左滑加载更早历史 | 出现 `endDate` 参数请求 | ✅ `stockCode=002636.SZ&endDate=20240411&limit=500` |
| 缩略条点击跳转 | 点击前后视窗截图不同 | ✅ 已变化 |
| 买卖点 B 标记 | 高清截图中红色圆点 + 字母 B | ✅ 2026-08-08 位置 |
| 无轮询 | 进入页面静置 10 秒的新增请求 | ✅ 0 个 |

**左滑的自动化方式有个坑**：用 `page.mouse` 拖拽无效——画线层的 canvas 会拦截 `mousedown`，拖出来的是画线预览而不是图表平移。必须用 `page.mouse.wheel()` 缩放视野来改变 `logicalRange.from`。

**缩略条点击已支持自动补页**（2026-11-04）：点击早于已加载窗口的日期时，会连续 `loadOlder()` 直到覆盖目标或达到上限（`MAX_SEEK_PAGES = 3`，约 1500 根）。实测点 30% 处（2022 年）触发两次补页：
```
stockCode=002636.SZ&endDate=20240411&limit=500
stockCode=002636.SZ&endDate=20220320&limit=500
```
随后视窗跳到 2022 年区间，无 pageerror。

**上限设 3 页的理由**：每页 500 根，3 页 ≈ 1500 根。再多就等于点一下把全历史拉进内存，窗口化的收益会被吃回去。超出上限时提示「已向前加载 N 页仍未覆盖该日期」，引导用户手动拖。

**一个已知偏差**：跳转后目标日期未精确居中，视窗落在目标日的右侧约半年处。不影响「能看到那段历史」的目标，但 `setVisibleLogicalRange` 的 idx 定位与预期有偏移，未深究。
