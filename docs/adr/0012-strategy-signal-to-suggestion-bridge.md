# ADR-0012：策略信号 → 建议单桥接 —— 实时信号口径

- 状态：已接受（2026-11-10）
- 关联：ADR-0011（策略接口与撮合口径）、ADR-0010（多用户凭证与 Agent 只读）、ADR-0007（bar 统一存储与时间轴）
- 依据：`docs/multi-market-rollout.md` 阶段 3（半自动交易）「策略信号 → 建议单」
- 落地：`backtest/live_signal.py`、`backtest/tests/test_live_signal.py`

## 背景

阶段 3 最后一块空白：`backtest/` 的策略只能对着历史出净值，信号出不了回测进程；
`okx_order_suggestion` 只能由人工或 Agent 问答写入。两边数据都在，中间少一段桥。

桥的方向只有一个：**信号流向建议单，不流向订单**。ADR-0010 决策 4 定下的「Agent 不下单」
不是靠代码里没人调用下单接口来保证的，而是靠这条链路上根本没有下单能力——
`OkxSuggestionService` 连 `OkxTradeService` 都没注入。桥接进程同理：它持有用户 JWT，
只能打 `/ai/suggest-order`，打不了 `/data/okx/trade/order`（那要走 requireWrite + 风控）。

## 决策

### 1. 决策依据是「最后一根已完结 bar」，未收盘的那根默认丢弃

回测里策略在 bar `i` 收盘后决策、次根开盘成交（ADR-0011 决策 2）。实时里没有「次根」，
所以「当前决策点」= **最后一道已完结 bar**。两条口径必须等价，否则回测赚、实盘亏会变成玄学。

风险在于 `/market/bars` 返回的最后一根可能是正在走的那根：close 随价格跳动，
拿它决策等于偷看未来，同一分钟内重跑会得到不同信号，与回测结论不可比。
因此默认用 `ts + period > now` 判掉未完结 bar（`drop_unclosed`），`--keep-unclosed`
只应该在看盘中预览时开。周期不认识（`1mo`）时不动——宁可放过也不错杀。

### 2. 去重放 runner 侧的状态文件，不放数据库

两层去重，都记在 `--state-file`（默认 `backtest/.state/<策略>-<标的>-<周期>.json`）：

| 字段 | 作用 | 不加会怎样 |
| --- | --- | --- |
| `last_bar_ts` | 同一根 bar 只决策一次 | 轮询每 60 秒刷一条同样的建议单 |
| `last_side` | 连续同向不重复写 | 趋势策略每根 bar 都写一条，人工确认页被淹 |

为什么不查「建议单表最近一条」：那需要给 Python 进程加一个读接口 + 用户令牌的读权限，
而它只需要写。状态文件还顺带解决了「进程重启」的连续性问题。

`--allow-repeat` 可以关掉 `last_side` 抑制，给分批建仓类策略用。
`last_bar_ts` 不能关——关掉就是主动放弃幂等。

**提交失败时不推进 `last_bar_ts`**：策略是确定性的，同一根 bar 重算得到同一个订单，
所以下次重试安全；反过来先推进就会把信号永久丢掉。

### 3. 默认市价单，`sz` 按 8 位小数格式化

策略只产出 `Order(side, size)`，没有价格——ADR-0011 决策 6 明确本阶段不做限价单。
硬凑一个限价（用收盘价）会造出「挂不上」的建议单，比市价更误导人工。

`sz` 用十进制字符串而非 float：`json.dumps` 会把 `0.0123` 写成 `0.0123`，
但 `1e-05` 会变成 `1e-05`，Java `BigDecimal(String)` 虽然能解析科学计数法，
日志和人工核对时却很难看。固定 8 位小数的代价是：OKX 各标的 `lotSz` 不同
（BTC 是 1e-8，部分币是 0.01 甚至 1），超出精度的 `sz` 会被 OKX 拒。
当前建议单只是记录、成交仍由人工确认，所以先按最细粒度格式化；
对齐 `lotSz` 需要 instruments 元数据，留到真正做自动下单时再补。

### 4. 写入走 `/ai/suggest-order`（用户 JWT），不走内部密钥

两条路都通，选 JWT 路径的理由：

- 内部路径 `/internal/okx/suggestion` 要求 `X-Internal-Key`，那是**服务身份**的凭据。
  一个跑策略的 Python 进程不是服务，让它拿内部密钥，等于把「服务间接口」的边界
  降级成「谁都能调」。
- JWT 路径自带 `userId`，审计里「谁的建议」是签名保证的，不靠调用方自觉传。
- 用户 JWT 会过期，天然限制了进程的有效期。

代价是：`/ai/suggest-order` 的 body 是 `Map<String,String>`，`confidence` 传不进去
（`SuggestionClient` 过滤掉了）。当前策略也算不出置信度，先不传；要传就得改
controller 的入参类型，那属于「Agent 建议」的语义，不该为了策略信号去动。

### 5. 持仓/现金是本地台账，不是账户余额

`ctx.position` / `ctx.cash` 是策略的必要输入：`SMACrossStrategy` 在 `position <= 0`
时才买、`position > 0` 时才卖。如果永远传 `position=0`，死叉永远不产生卖单——
看起来「策略不灵」，实际是输入错了。

首版用「state 里的估算台账」：每次成功提交后按信号 bar 收盘价和**实际提交的 `sz`**
增减仓位与现金。它只服务下一次决策，**不追求与 OKX 账户一致**。
人工拒单、手动加减仓之后台账就漂了，所以 `--position` / `--cash` 是校准入口。

为什么不每次去查 `/data/okx/trade/positions`：那需要给进程加读权限，而
「只写建议单」是这条链路的边界；且查到的持仓含手续费扣减、冻结等口径差异，
反而更难解释。台账漂移是可观测的（state 文件是人可读的 JSON），比隐式口径更诚实。

## 后果

- 「回测 → 实时信号 → 人工确认 → 模拟盘下单」闭环打通，环上的每个断点都有明确归属：
  策略在 `backtest/`，信号在 runner，建议单在 data-service，成交由人点。
- runner 是**无状态服务 + 有状态文件**的组合，多实例并发跑同一策略会互相覆盖 state。
  当前只打算单实例定时跑（cron / 手工），要水平扩展得先把 state 挪到 Redis 或加锁。
- 台账与真实账户会漂。止损线、可用余额这类判断不能读台账，必须读账户。
- `--ord-type limit` 分支已实现（策略带 `px` 时生效），但 `Order` 目前只有两字段，
  实际不可达。留着是为了 `Order` 扩展时不用改 runner。

## 已知风险

1. **未完结 bar 的判定依赖周期长度**：`1mo` 无法判断（月长不固定），直接放过。
   若某标的的 bar `ts` 不是开盘时刻（历史遗留数据），`ts + period > now` 会误判，
   表现是「总是丢最后一根」，可用 `--keep-unclosed` 绕过并回查数据口径。
2. **state 文件损坏会阻塞运行**（故意抛错，不静默重置）。静默返回空态会导致重复写建议单，
   比报错难排查得多。修法是删文件或手工修正 JSON。
3. **信号只代表「这根 bar 收盘时的判断」**，到人工确认时价格可能已走远。
   建议单不设有效期，执行前必须自己看一眼现价——这是「人工确认」的意义，不是缺陷。
