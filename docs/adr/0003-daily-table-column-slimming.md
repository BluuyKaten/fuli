# 0003 - 日线表字段类型瘦身（VARCHAR(9) + INT 日期）

- 状态：已采纳
- 日期：2026-11-03

## 背景

`stock_daily_data` 当前 7,663,187 行，数据 901 MB、索引 583 MB，索引/数据比 0.65。`EXPLAIN` 显示查询命中 `uk_code_trade_date` 时 `key_len=164`。

拆开这 164 字节：`stock_code VARCHAR(32) utf8mb4` = 32×4+2 = 130，`trade_date VARCHAR(8) utf8mb4` = 8×4+2 = 34，合计正好 164。也就是说，**索引里每条记录有 164 字节纯粹用来定位，而业务数据本身只有约 120 字节**——索引比它索引的东西还占地方。

## 决策

1. `stock_code`：`VARCHAR(32)` → **`VARCHAR(9)`**，保持 utf8mb4。
2. `trade_date`：`VARCHAR(8)` → **`INT`**，存 `20231103`。
3. 主键、唯一键结构不变，只改列类型。`uk_code_trade_date` 重建后 `key_len` 预期降到 42（9×4+2 + 4）。

预期索引体积：583 MB × 42/164 ≈ **150 MB**，同等 buffer pool 下可缓存的行数增加约 3.9 倍。

## 实测结果（2026-11-03 执行后，修正了上面的预期）

迁移耗时 **1 分 38 秒**，行数 7,663,187 保持不变，抽样数据一致。

| 指标 | 迁移前 | 迁移后 | 结论 |
|---|---|---|---|
| `key_len` | 164 | **42** | ✅ 符合预期 |
| 索引体积 | 583 MB | **498 MB** | ❌ 只降 15%，不是预期的 150 MB |
| 全历史查询（5,071 行） | 6.03 ms | **6.1–7.6 ms** | 持平，无加速 |
| 3 年窗口查询（727 行） | 0.97 ms | 2.06 ms（冷）→ 预热后持平 | 无变化 |

### 为什么「预期 150 MB」是错的

我按 `key_len` 线性换算体积，这一步是错的。`key_len` 报的是索引键的**最大可能字节数**（utf8mb4 按 4 字节/字符预留），而 InnoDB 的 `VARCHAR` 是**变长存储**——`600519.SH` 这种纯 ASCII 内容实际只占 1 字节/字符。

真实条目宽度（含二级索引隐含的主键 8 字节）：

- 迁移前：`stock_code` 9 字符 + 2 字节长度前缀 = 11，`trade_date` "20231103" 8 + 1 = 9，主键 8 → **28 字节**
- 迁移后：`stock_code` 9 + 1 = 10，`trade_date` INT = 4，主键 8 → **22 字节**

28 → 22 是 21%，实测 15%，差额来自页填充率。**`key_len` 从 164 降到 42 是真的，但它不代表索引缩小了 4 倍。**

### 这次改动的真实价值评估

**它不是一个性能优化，我不该把它排在窗口化和缓存之前。**

- 收益：索引小 15%，查询性能持平，类型语义更正确（`INT` 能直接比较大小和做区间，`VARCHAR` 存日期依赖字面量格式）
- 成本：1 分 38 秒停机 + 一轮跨模块代码改动 + 隐式转换的回归风险

如果重来一次，正确顺序是：先做窗口化（传输占 54.7%）和 `shallowRef`（前端占 42.5%），最后再考虑字段类型——因为它只影响那 2.8% 的数据库环节。

保留改动而不回滚的理由只有一条：`INT` 存日期是正确的数据建模，且已经避免了字符串参数触发的隐式转换。留着不会更差。

## 关键修正：为什么是 VARCHAR(9) 而不是 CHAR(9)

我最初建议 `CHAR(9)`，这是错的，两个原因：

1. **CHAR 按字符数预分配字节**。utf8mb4 下 `CHAR(9)` 定长占 36 字节，而 `VARCHAR(9)` 存 `600519.SH` 这种纯 ASCII 只需 9 字节内容 + 1 字节长度 = 10 字节。VARCHAR 反而更省。
2. **CHAR 会尾部补空格**，而 `StockDataController.withSuffixIfBare` 说明系统里确实存在**不带后缀的裸代码**（`600519`）。一旦某处写入或比较裸代码，`CHAR(9)` 会把它补成 `600519   `，导致 `= '600519.SH'` 之外的所有等值匹配行为变化。这是静默的数据正确性问题，不是性能问题。

VARCHAR(9) 的代价是索引里多 2 字节长度前缀（38 vs 36），可以忽略。

## 备选方案与取舍

- **列级 `CHARACTER SET ascii`**（否决）：能让 `key_len` 降到 14 字节，比 42 又省 3 倍。但 JDBC 传入的参数是 utf8mb4，跨字符集比较依赖 MySQL 的隐式转换，一旦优化器放弃索引就退化成全表扫描——为省 100 MB 冒全表扫描的风险不值得。
- **保持 VARCHAR(32) 不动**（否决）：索引会随数据线性膨胀，且 32 字符对 A 股代码是 3.5 倍冗余。
- **加覆盖索引 `(stock_code, trade_date, close_price, ...)`**（暂缓）：能让 K 线查询免回表，但会把索引体积重新推高，与本次瘦身目标冲突。等窗口化落地、实测确认回表是瓶颈后再评估。

## 后果

- `StockDailyData.tradeDate` 从 `String` 变 `Integer`，所有 `String.valueOf(row.get("tradeDate"))` 的调用点必须验证：`LocalDate.parse("20231103", BASIC_ISO_DATE)` 仍可工作，但 `PracticeSnapshotLoader` 里的边界校验依赖字符串比较顺序，需改为数值比较。
- 任何 `WHERE trade_date BETWEEN '20230101' AND '20251231'` 的字符串字面量会因隐式类型转换而**失去索引**，必须改为整型参数。这是迁移中最容易漏的一处。
- 迁移需停机重建表，766 万行约 2–5 分钟。
- 索引缩小后 `EXPLAIN` 的 `key_len` 是验收指标，必须实测确认降到 42 附近。
