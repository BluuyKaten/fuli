# ADR-0017：资产曲线取数窗口 —— 按持仓区间收窄，而不是合并两次拉取

- 状态：已接受（2026-11-11）
- 关联：ADR-0016（分析聚合下沉的边界）、ADR-0002（K 线窗口化加载）
- 落地：`analysis-service/.../AnalysisService#getAssetCurve`、`#priceWindows`

## 背景：先纠正 ADR-0016 的一个错误前提

ADR-0016 写过「`getAssetCurve` 与 `getPerformanceStats` 在同一次页面加载里各自拉一次全量交易，
可以合并成一次」。动手前核对了实际调用图，**这个前提不成立**：

| 页面 | 请求 |
| --- | --- |
| 仪表盘 `DashboardPage` | `/analysis/dashboard`、`/analysis/monthly-profit`、`/analysis/asset-curve` |
| 绩效页 `PerformancePage` | `/analysis/performance` |
| 报告页 `ReportPage` | `/analysis/performance` |

两个吃全量交易列表的端点**从不同时出现**在一个页面里。所以「合并成一次拉取」即使做了，
也省不下任何一次 Feign 调用——那是一段为了看起来合理而写的死代码。

真正的读放大在同一个方法内部：`getAssetCurve` 对**每只股票各发一次** `getDailyData`，
而且区间一律是「全账户最早交易日 → 今天」。

## 决策

每只股票只拉自己**持仓窗口**内的日线：

- 起点 = 该股首笔交易的交易日；
- 终点 = 该股末笔交易的交易日；若末笔之后仍持有（净买入为正），延伸到 `endDateActual`。

为什么安全：估值循环只在 `quantity > 0` 的日期读价格，而 `quantity > 0` 必然落在
「首笔买入 ~ 最后一笔卖出（或今天）」这个区间里。窗口之外的日期要么还没买、要么已清仓，
读到价格也不会被使用。

## 为什么不顺便把 N 次调用合成 1 次

批量化需要新的 data-service 端点（现在只有单标的 `/data/stock/daily`）+ Feign 方法 + 契约文档，
而收益只是**往返次数**，不是载荷体积（同样多的行，换个信封）。先把「拉错区间」这个真正的
浪费消掉；批量端点等有第二个调用方需要时再做。

## 约束与验证

- 窗口收窄是**纯性能改动**：曲线的 `dates` 与 `assets` 必须逐点不变。
  `AssetCurveFetchWindowTest` 把改动前的实现照搬进测试当参照物，用同一份数据跑两遍比较；
  同时断言每只票实际被请求的区间（已清仓的止于末笔、仍持有的延伸到 endDate）。
- 做了反向验证：故意把「仍持仓」的窗口截短，两条断言都会红——避免写出永远绿的测试。
- 注意 `priceWindows` 依赖交易列表已按交易日升序（方法内先 `sort`），否则「首笔/末笔」不成立。

## 后果

- 一个 2020 年清仓的标的，不再在每次打开仪表盘时被拉着补 6 年日线。
- 往返次数仍是「每只持仓标的 1 次」：持仓 10 只就是 10 次串行 Feign，延迟仍是叠加的。
  这是下一个可优化点（批量端点或并发取数），本次刻意不做，避免一次改两件事。
