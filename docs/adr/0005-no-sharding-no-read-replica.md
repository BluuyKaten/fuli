# 0005 - 明确不做分库分表和读写分离

- 状态：已采纳
- 日期：2026-11-03
- 关联：0003（字段瘦身）、0004（缓存）

## 背景

讨论性能方案时，「生产级」被理解为「应该上分库分表 + 读写分离」。这是一个需要显式拒绝的默认假设——如果不写下来，下一个维护者会以为是漏做，然后补上一套没有收益的分片逻辑。

## 决策

**不做分库分表，不做读写分离。** 同时保持「分片就绪」。

当前规模与判据的对照：

| 维度 | 当前 | 需要考虑分片的起点 | 余量 |
|---|---|---|---|
| 单表行数 | 766 万 | 2,000 万 | 2.6× |
| 单库体积 | 1.5 GB | 500 GB | 330× |
| 写 QPS | 收盘后批量 | 千级 | 数个数量级 |

## 为什么读写分离在这里是负收益

这个库的访问特征不是「读多写少」，而是**读多、写极集中且陈旧容忍度为零**。日线同步任务在收盘后批量写入，写入完成后立刻就有用户去看这批数据。主从复制延迟（即使只有 50 ms）会导致「同步页显示成功、K 线图没有新数据」这类问题，而这类 bug 的归因成本远高于它节省的那点主库压力。真要减压，缓存（ADR-0004）是正确工具。

## 为什么分片是负收益

`PracticeSnapshotLoader` 需要按股票拉 3 年区间并做连续性校验，`stock_info` 与日线存在跨表关联。一旦按 `stock_code` 分片，任何「全市场某日」类的查询（涨跌幅排行、板块统计）都退化为广播查询加内存聚合。用 0 的吞吐收益换取这套复杂度，是纯亏损。

## 保持分片就绪的做法

1. 数据访问层收敛到单一入口（`KlineQueryRepository`），不让 SQL 散落在 controller 和 service 里。
2. **分片键确定为 `stock_code`**——所有 K 线查询天然带它，是唯一不用改查询就能切开的维度。
3. 表名通过配置项引用，不硬编码。
4. 本文档即「明天要分怎么分」的说明：读写路径已全部按 `stock_code` 收敛，分片时只需替换 Repository 实现。

## 后果

- 需要监控行数增长。数据同步若扩展到分钟线，量级会从 766 万跳到 3 亿/年，届时本决策立即失效，必须重新评估（分钟线更适合列式时序库而非分片 MySQL）。
- 「为什么不分片」必须在答辩和代码注释里能一句话说清，否则会被当成疏漏。
