# 0002 - K 线按视窗加载，不再全量返回

- 状态：已采纳
- 日期：2026-11-03

## 背景

K 线页的日线接口 `/stock/daily` 只接收 `stockCode`，`StockDataController.queryDaily` 无条件 `selectList` 全量返回；分钟线走东方财富接口时固定 `lmt=5000`，同样一次拉满。前端 `LightweightChart.vue` 把结果直接塞进 `ref<CandleItem[]>([])`，Vue 对数组做深度响应式，5000 个对象、每个 6 个字段全部被 `Proxy` 递归包裹，随后 8 个技术指标各遍历一遍全量数据生成新的对象数组。

实测数据：`data_db.stock_daily_data` 共 7,663,187 行、5,596 只股票，单股最大 5,071 行。日线本身尚可承受，但分钟线一次 5,000 根、且每次请求都穿透到外部 API，是更重的一条链路。

跨度一大就卡，根因不是 MySQL 慢，而是「一次把全量数据交给浏览器」。

## 决策

1. **默认只加载最近 500 根**。1200px 宽的图区画 500 根已是每根 2.4px，再多也分辨不出，传输和渲染都是浪费。
2. **向左浏览时按需向前加载**，每次 500 根，直到上市日。不做无限预加载。
3. **首次加载同时返回一条降采样的全历史骨架**（约 240 点），用于图表底部的全貌缩略条，解决「窗口化后失去全历史直觉」的交互退化。
4. **指标只计算「视窗区 + 前置窗口」**，不覆盖全量。前置窗口长度取所有指标的最大回看需求（MA60 需要 59 根），随请求一并取回但不渲染。此处用「视窗区」而非「可见区间」，避免与词汇表里的「可见行情」（盲测练习概念）混淆。
5. **前后端契约显式化**：`getStockDailyData` 增加 `startDate` / `endDate` / `limit` 参数，后端已有的 `startDate` / `endDate` 分支从死代码变成主路径。

## 备选方案与取舍

- **保留全量返回，只把 `ref` 改成 `shallowRef`**（否决）：改动只有一行、收益立竿见影，但那是治标。数据量随时间线性增长，两年后同样退化，且每次切换周期仍要重新传输和重算全量。
- **前端虚拟滚动 + 只渲染可视区**（否决）：`lightweight-charts` 内部已按像素抽稀，渲染不是瓶颈；真瓶颈是传输和响应式代理，而虚拟滚动仍要求全量数据驻留内存，解决不了这两点。
- **服务端预计算并缓存全部指标**（否决）：指标参数（MA 周期、MACD 快慢线）是前端可配的，服务端穷举组合不现实；把计算留在前端反而更灵活。

## 后果

- **CSV 导出只能导出已加载区间**。要保留「导出全历史」，需单独提供一个流式导出接口，不能复用页面加载路径。
- **窗口边界的指标必然为空**。若不额外取前置数据，左边缘前 59 根的 MA60 会是断的。前置窗口因此是决策的一部分，不是优化项。
- **缩略条需要新的轻量接口**。只读 `trade_date + close_price` 两列，服务端降采样后返回约 4 KB，与主图窗口解耦。
